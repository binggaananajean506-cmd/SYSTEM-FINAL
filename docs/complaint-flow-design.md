# Simpler complaint management

The complaint list and case dialog should answer: which case is this, what is its status, and what needs to happen next? Audience: barangay staff handling real cases and authorized oversight users. Keep the existing green identity, use a quieter workspace, plain language, and existing native controls. No new dependencies, changes to case data, permission expansion, or changes to the six-round backend workflow.

The five queues are mutually exclusive: New complaints (newly filed records without a hearing history), Needs action (reviewed cases, past hearings awaiting a result, next schedules, old records needing confirmation, and CFA review), Hearings (upcoming appointments), Waiting for resident, and Closed. Show actual case references, both parties, the complaint, status, a plain next step, and Open case. Keep search scoped to the selected queue and show a short queue description and result count. Empty search results should offer clear recovery.

The case opens with the parties and a readable complaint summary, followed by the current next action within the first viewport. Remove the five-stage stepper and repeated formal record banners. Show one main action; separate attendance choices only when the hearing time has arrived. Keep practical schedule and summons actions together. Move secondary exceptions, full details, hearing records and activity history into clearly labeled native disclosure sections. Clean only known leading [Problem:] and [Location:] metadata from the displayed narrative; preserve the underlying submission and original record.

Use short action labels: Review complaint, Prepare summons, Confirm given to tanod, and Schedule next hearing. After a successful background review, offer Set hearing without interrupting other work. Before the hearing time, do not offer a result entry action. At the hearing, ask whether both parties attended, then show the appropriate existing result or attendance form. Keep six rounds (three barangay, then three lupon), eligibility confirmation, document generation/printing, version checks, retries, and all server authorization intact. Keep complete history accessible.

Verify new, reviewed, waiting, future scheduled, notice pending, notified, due, next-round, old-record, CFA-pending, resolved and CFA-issued cases. Check empty search, long names/narratives, missing optional fields, failed saves with retry, and readonly/authorized access boundaries. Preserve the existing summons and CFA regression tests and add meaningful tests for exclusive queues, narrative display and the primary next action. Review desktop 1440x900 and mobile 390x844 in light and dark themes, keyboard navigation, disclosure access, overflow and action visibility. Save screenshots/evidence under output/complaint-review/ and run the design evidence checker. Rebuild, stage and deploy Hosting after completing the change; do not rebuild the APK.
