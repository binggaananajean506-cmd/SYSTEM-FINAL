# Complaint queues, hearing validation and concern cleanup

Newly filed complaints with no recorded hearing/history now appear in New complaints, immediately before Needs action. Reviewed cases, due hearing results, later-round scheduling and legacy confirmation stay in Needs action. Upcoming hearings, Waiting for resident and Closed retain their queues. Counts remain exclusive; reviewing a new case moves it into Needs action. Existing workflow/status data is not migrated.

Next-hearing scheduling previously prefilled a date and 09:00 time. Choosing today after 09:00 resulted in the server rejecting a past appointment. The new appointment now requires an explicit date and time, labeled Philippine time, and is validated against UTC+8 before queuing. Invalid times keep the form, attendance and notes intact. Backend future-time and six-round restrictions remain enforced. A same-day future appointment is allowed; recording absence completes that round and schedules the next one under the existing workflow.

The concern Actions page, Single Reports three-dot menu, Group Reports Action menu and case-list menu expose Delete concern for approved administrators and captains, vice captains and secretaries in the concern's own barangay. Each entry opens the same confirmation naming the concern and then uses the existing background activity panel. The callable rechecks authorization, rejects complaint/non-concern records, and atomically deletes the submission plus its public summary while keeping an audit entry. Repeating the original actor's completed deletion is safe. Existing audit data, attachments and subordinate historical report documents are retained; there is no bulk or recursive file deletion. Public-summary synchronization reads the latest source in a transaction so an older event cannot recreate a deleted concern summary.

Validation includes authorization across all 42 barangays, cross-barangay/role denial, required confirmation, failure retention, idempotent retry, five exclusive queues, first-review queue movement, and the reported non-attendance scenario using the actual server workflow planner. No production concern is deleted for testing. Build and deploy the delete callable and updated summary trigger, then build/stage/deploy Hosting. The APK is unchanged.
