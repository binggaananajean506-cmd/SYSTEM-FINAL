# Complaint deletion

Open case and Delete appear inside each row's three-dot Actions menu in every complaint queue. Delete also remains in the case dialog footer. The popover stays above the scrolling table, fits within the viewport, and supports keyboard navigation, Escape and outside-click dismissal. Confirmation identifies the case and resident, explains that deletion cannot be undone, and offers Keep complaint. The original case remains in local state until the server confirms success. Deletion uses the existing floating submission activity and the same per-case lock as complaint updates, including retry and account-switch protection.

The deleteComplaint callable checks the approved caller, current office access, a valid complaint reference, explicit confirmation, record kind, and current barangay scope. Permissions match concern cleanup: super administrators or the same barangay's captain, vice captain and secretary. Other roles and cross-barangay requests are rejected. Concern and complaint endpoints cannot delete each other's record types.

A transaction removes the submissions document (including its embedded hearings and summons) and creates an audit receipt. The receipt permits safe retry by the original actor when a successful response was lost. Audit records, uploaded files and operational subcollections are retained, matching concern cleanup; this is list/case cleanup rather than a recursive data purge. No production complaints are deleted by tests or deployment.

Verification: functions/complaint_cleanup.test.js exercises the actual callable, authorization across all 42 barangays, confirmation, wrong record types, reference validation and safe retries. admin_web/tests/complaint-delete.spec.js covers both entry points, cancellation, waiting for server confirmation, unrelated records, failures/retries and hidden controls. Deploy functions:deleteComplaint, then follow the required admin build, hosting staging and Hosting deployment pipeline.
